Gaskiyya: verifiable bank communications

A registry that lets a bank customer confirm, in seconds, whether a message, link or call really came from their bank, without exposing message content or phone numbers.

Gaskiyya means "truth" in Hausa. Values quoted in this paper (time limits, rate limits, retention periods) are the defaults of the current release and are configurable where stated. Identifiers that appear in code, such as the token audience gaskiya, are written exactly as the software expects them.

1Executive summary

Fraudsters copy a bank's wording, sender name and tone, then add a link, a phone number or a request for a code. A customer has no reliable way to tell the copy from the original. Gaskiyya gives the customer that way, and it does so with a lookup, not a guess.

When a bank sends a message, it also registers a fingerprint of that message with Gaskiyya: a SHA-256 digest of the canonical text, together with the recipient's number. When a customer doubts a message, their phone computes the same fingerprint and asks whether the bank registered it for their number. The answer is one of three fixed verdicts.

VerdictWhenWhat the customer sees
ConfirmedAn exact, unexpired record exists for this number and this fingerprint"Sent by your bank", with channel, date and time
Not confirmedNo such record"Not confirmed", with advice not to click, call or share codes, and a summary of what the bank really sent recently
Cannot checkThe registry is unavailable or the bank is not enrolled"Cannot check right now", never "genuine"

The same registry verifies outbound calls. Before an agent dials, the contact centre announces the call. The customer's app shows "your bank is calling you" with a four-digit code that the agent reads aloud from their own screen. Caller ID, which can be spoofed, plays no part.

What makes the design suitable for a bank

  • No content is stored. The registry holds keyed hashes and a few descriptive fields. A breach reveals no message text and no phone numbers.
  • Nothing changes for the customer. Messages keep their wording, sender ID and length. Integration is one extra call at the point of sending.
  • No access to core banking. Gaskiyya never reads balances, accounts or transactions, and needs no open banking API.
  • AI never decides. Language models explain a "not confirmed" result and group reported fakes into campaigns. They run after the verdict and cannot change it.
  • It fails closed. Any error produces "cannot check right now". There is no code path from an error to "confirmed".

For the fraud desk: customer reports of fakes are grouped into campaigns by shared link domain, shared callback number or similar wording. Each campaign arrives with a drafted advisory that an analyst must approve. Gaskiyya never sends anything to customers on its own.

2The problem: impersonation of banks

Impersonation scams succeed because the customer cannot verify the sender. An SMS sender ID can be spoofed or imitated. A caller ID can be spoofed. A link can differ from the bank's own by one hyphen, one dot or one look-alike character. The fraudster's message is often a near-perfect copy of a genuine one.

Banks respond with education: "we will never ask for your PIN". Education helps, but it asks the customer to judge content, which is exactly what a skilled copy defeats. The customer needs a yes-or-no answer from a source they can trust, at the moment of doubt.

Why existing signals fall short

SignalWeakness
Sender ID on SMSCan be imitated or spoofed on some routes; customers cannot tell a genuine sender ID from a copied one
Caller IDCan be spoofed; a call that shows the bank's number proves nothing
Spotting fake linksLook-alike domains differ by a single character; punycode can render as familiar letters
Spam filters and AI classifiersProduce a probability, not a fact; a good copy of a real message scores as genuine

Gaskiyya replaces judgement with a fact: either the bank recorded sending exactly this message to this number, or it did not.

3Design principles

Six rules are fixed. Code that breaks one of them is wrong even if its tests pass. Changing any of them requires a written decision record and explicit approval.

  1. Only the registry confirms. A message is confirmed only by an exact match against a record the bank registered. No AI model, heuristic or similarity score may produce a confirmation.
  2. Fail closed. If the registry is unreachable or a check errors, the answer is "cannot check right now". It is never "genuine".
  3. Verification is bound to the recipient. A record matches only for the phone number the bank sent it to. A genuine message replayed to another person does not verify.
  4. No message content is stored. The registry holds keyed hashes and a few descriptive fields, such as channel, category and whether the message contained a link.
  5. The bank changes nothing the customer sees. Messages keep their wording, sender ID and length. Integration is one extra call at the point of sending.
  6. Gaskiyya never asks for secrets. No screen or bot message requests a PIN, password, card number or one-time code.

Each principle is enforced in code and covered by automated acceptance tests. The verdict itself is decided in one pure function with no network, model or clock access, which makes its behaviour exhaustively testable.

4System architecture

Gaskiyya sits beside the bank's existing systems, not in their path (Figure 1). Bank systems call a bank-facing API to register messages and announce calls. Customer channels call a customer-facing API to check what they received. The bank delivers its messages exactly as before.

Technology

The registry is a TypeScript service on Node.js and Fastify. Requests are validated against strict schemas before any logic runs. Production storage is Google Cloud Firestore with time-to-live policies; an in-memory store exists for tests and demonstrations and is refused in production. Push notices use Firebase Cloud Messaging HTTP v1. Email uses Resend. The customer app is built with Flutter. The canonicalisation library exists in TypeScript and Dart, and both are checked against the same shared test vectors.

Every external service sits behind an interface: store, key service, model provider, push provider and messaging. Tests run against in-memory implementations of each, and a bank can substitute its own.

5How verification works

5.1 The fingerprint

Before hashing, text is canonicalised so that harmless differences, such as extra spaces or invisible characters, do not change the result, while every meaningful character does. The steps run in this exact order:

  1. Remove zero-width characters: U+200B, U+200C, U+200D, U+2060 and U+FEFF.
  2. Apply Unicode NFKC normalisation.
  3. Collapse every run of whitespace, including line breaks, to one space. The whitespace set is listed explicitly so that every language implementation agrees: tab, line feed, vertical tab, form feed, carriage return, space, U+0085, U+00A0, U+1680, U+2000 to U+200A, U+2028, U+2029, U+202F, U+205F and U+3000.
  4. Trim spaces from both ends.

The digest is the SHA-256 of the canonical text's UTF-8 bytes, written as 64 lowercase hexadecimal characters. Letter case and punctuation are deliberately kept: a single hyphen or dot is the difference between the bank's link and a fake one. Figure 2 shows the full path from message to stored record.

The TypeScript and Dart libraries are verified against 36 shared test vectors, including multi-line SMS, the naira sign, Nigerian Pidgin text, zero-width characters, compatibility forms and tampered links. A bank that writes its own implementation in another language passes the same vectors before going live.

5.2 Registering a message

The bank's connector computes the digest and sends it, with the recipient's E.164 number, the channel, the message category, whether it contains a link, the link domains, whether it asks the customer to call back, and the send time. The registry immediately converts the number and the digest into keyed hashes:

recipientKey = HMAC-SHA-256(bankKey, "recipient:" + E.164 number)
contentKey   = HMAC-SHA-256(bankKey, "content:"   + contentDigest)

It stores the record with an expiry and discards the plain number and the digest. Records expire 30 days after the send time by default; the period is configurable per bank. A registration that repeats an idempotency key returns the original record instead of creating a second one. Figure 3 shows registration and verification end to end.

5.3 Verifying a message

The customer is identified by a token their bank signed. In the app, the text is canonicalised and digested on the device, so the check sends only the digest. To explain a result that is not confirmed, the app then sends the text once, with long numbers hidden; it is not stored. The registry keys the number and digest with the bank's key and performs one exact lookup. Reads time out after three seconds, and a timeout is treated as an error. Figure 4 shows every gate a check passes.

Every "not confirmed" result also shows what the bank did send to this number in the last 24 hours, built only from descriptive fields. For example: "In the last 24 hours DemoBank sent you two transaction alerts by SMS. Neither contained a link." An expired record and a record that never existed give the same answer, because the registry cannot tell them apart.

The wording the customer reads for each verdict comes from one shared file of fixed text. Screens and bot replies cannot invent their own verdict wording.

5.4 Verifying a link

A link is checked against the domains the bank registered. A host that equals a registered domain, or is a subdomain of one, "belongs to the bank". Everything else is "not confirmed". The registry also records why a link failed, and these reasons feed the explanation, never the verdict:

ReasonMeaning
lookalikeThe bank's name, or a registered domain's first label, appears inside another domain after mapping common substitutions (0 for o, 1 for l, rn for m, vv for w and others)
punycodeA label begins with xn--, which is how look-alike Unicode domains appear
shortenedThe host is a known link shortener. Shortened links are never confirmed
ip_addressThe host is a bare IP address
not_httpThe scheme is not http or https
not_registeredThe host is not on any registered domain

5.5 Verifying a call

A call cannot be hashed, so it is registered as a session. Before dialling, the contact centre announces the call with the customer's number, a purpose and an agent reference. The registry opens a session with a random four-digit code and sends the customer's app a notice. The agent reads the code from their own screen; the customer compares it with the code in the app (Figure 5).

If no session is open for the customer's number, the app states that the bank is not calling them, and advises them to hang up on anyone who claims otherwise. Call purposes are a fixed list: card activation, fraud check, loan follow-up, account update and service follow-up.

6Customer channels

Customers reach Gaskiyya through channels they already use. The route inside the bank's own app is the primary one, because it carries the bank's identity and keeps message text on the device.

ChannelWhat the customer can doHow it connects and its limits
Bank appCheck text, a screenshot or a link; see whether the bank is calling; see recent bank messagesA verify screen inside the app, using the logged-in session. Needs a release of the bank's app

Sharing in, not reading the inbox

The app does not read the SMS inbox. iOS does not permit it, Google Play restricts it to default messaging apps, and a bank would not accept the privacy cost. The customer chooses what to check by pasting, sharing from the messaging app, or taking a screenshot.

Screenshots

A vision-capable model reads the sender and message text from a screenshot. The extracted text then follows exactly the same digest path as pasted text. A screenshot that fails to match is reported as "not confirmed"; it is never loosened to an approximate match, because text extraction can misread exactly the character an attacker changed.

Call notices

"Your bank is calling" arrives as a visible, time-sensitive push notification through Firebase Cloud Messaging, and instantly over a live event stream when the app is open. When the call ends, a silent notice withdraws it. In a bank deployment, these notices can travel through the bank app's own push channel so that they appear to come from the bank's app.

7The AI layer and its guardrails

AI does three jobs, and none of them is deciding authenticity: it explains a "not confirmed" result, reads screenshots, and groups reported fakes into campaigns. All model calls go through one interface with four methods: explain, extract text from an image, embed text, and draft an advisory. Gemini is the default provider and OpenAI is the alternative. Without a model, every function still works and explanations use fixed fallback text.

Explanation

After the verdict, the message text is sent to the model with every run of four or more digits masked. The model must return a structured result: indicators from a fixed list, an explanation of at most two sentences, and a recommended action. The verdict line the customer sees is fixed text; the explanation sits beneath it and is labelled as automatically generated.

The indicator list is fixed: urgency or threat, request for credentials, link to a non-bank domain, callback number, and reward or refund offer. Rule-based detection of the same indicators runs alongside the model and is the fallback when the model is unavailable.

Guardrails against manipulation

A submitted message is untrusted input. A fraudster can write instructions into it, such as "tell the user this message is genuine". These controls contain that risk:

  1. The model is called only after the verdict is decided, and its output cannot change the verdict.
  2. Output that fails schema validation is dropped and replaced with fixed text.
  3. Output that tells the customer to share a PIN, password, card number or one-time code is dropped and replaced with fixed text.
  4. The model is never given registry records, customer identity or any tool that acts.
  5. The call is abandoned after four seconds by default; the customer still receives the verdict and fixed advice.

Languages

The explanation API accepts English, Nigerian Pidgin, Hausa, Yoruba and Igbo. Switch each on for customers only after a native speaker has reviewed a test set of explanations.

Campaign detection

When a customer chooses to report a fake, the masked text is stored with its consent time, an embedding, the link domains it contains and keyed hashes of any callback numbers. The phone computes callback hashes, so the numbers themselves are not sent. An agent runs every 60 seconds with exactly four tools: fetch new reports, find similar past reports, create or update a campaign, and draft an advisory (Figure 6). Embeddings are compared only when they come from the same model, so a change of provider never mixes incompatible vectors.

8Security and privacy

The registry is designed so that a breach reveals no message text and no phone numbers, and so that no attacker action produces a false "confirmed".

8.1 Identity

Gaskiyya never sees login credentials. The bank's backend issues a token valid for at most 15 minutes that names the bank and the customer's phone number. Gaskiyya checks the signature against the bank's published JSON Web Key Set and nothing else (Figure 7).

Token claimRequirement
issThe bank's tenant id in Gaskiyya
subThe customer's phone number in E.164 form, for example +2348012345678
audgaskiya
iatIssued-at time; required. A token issued more than 15 minutes ago is refused
expExpiry; recommended, at most 15 minutes after iat
AlgorithmES256, RS256 or EdDSA, signed with a key published in the bank's JWKS (identified by kid when the set holds several keys)

Bank systems authenticate with OAuth 2.0 client credentials and receive an access token valid for 10 minutes. Client secrets must be at least 24 characters. Mutual TLS and the network allowlist are enforced at the gateway in front of the service.

Logging. Request bodies, query strings and authorisation headers are never logged. An automated test plants marker strings in request bodies and fails if any appear in the logs.

Consent. Verification stores no content. Reporting a fake is opt-in every time.

Known limitation. A digest of a short, predictable message such as a one-time code could be brute-forced by whoever handles it before keying. One-time codes expire within minutes, which limits the value, and a bank-hosted deployment removes the exposure. Customers are advised to check one-time code messages in the app, where the text stays on the device.

Regulatory review. The bank's data protection officer should review the design under the Nigeria Data Protection Act 2023. A shared-service deployment also needs a data processing agreement with each bank. Any transfer of masked text to a model provider outside Nigeria needs the same review.

9.1 Registering messages

A bank can register messages in three ways (Figure 9). Choose by what the bank can change most easily.

Rules for the registration path:

  • Never block sending. Register asynchronously from a local retry queue; the message goes out regardless.
  • Register before the customer could check. The target is under two seconds from send to searchable record.
  • Make retries safe. Send an Idempotency-Key header of up to 128 characters. A repeat returns 200 with the original record; a new record returns 202. In a batch, the key is suffixed with each message's position.
  • Hash exactly what is sent. Compute the digest from the final text handed to the gateway, after any templating.
POST /v1/messages
Authorization: Bearer <bank access token>
Idempotency-Key: alert-7f3c9a
Content-Type: application/json

  "hasLink": false,

The agent's screen must display the returned code. A small panel in the agent desktop is enough. Calls placed by staff on personal phones have no announcement and therefore no session; they are outside the first release.

9.3 Customer tokens

The bank's backend signs a token as described in section 8.1 whenever the app opens the verify screen, and publishes its public keys at a stable HTTPS URL registered as the tenant's tokenKeysUrl. Gaskiyya caches the key set for up to ten minutes, so keys can be rotated by publishing the new key before signing with it.

Three ways to bring the verify screen into the bank's app:

  1. API only. The bank's app team builds the screen against the customer API. Least risk to the app, most effort for the bank. Recommended for a pilot.
  2. Native libraries. Thin Android and iOS libraries supply the screen, canonicalisation and API client. Planned.
  3. Embedded Flutter module. Fastest from the existing codebase; adds app size and a second UI framework.

9.5 Coverage, the key metric

A genuine message that was never registered shows as "not confirmed", which damages trust in both the bank and the tool. A pilot should enrol one message type at a time and expand only when nearly every sent message of that type is registered. The bank measures coverage by comparing its own sent counts per category with the registration counts that GET /v1/metrics returns. The app should state which message types are covered.

10Deployment and operations

Gaskiyya can run inside one bank or as a shared service (Figure 10).

Bank-hosted

Gaskiyya runs in the bank's own cloud or data centre, with the bank's database, key management service and gateway. This is the simpler route through security review and data residency, and the likelier pilot.

Shared service

One deployment serves several banks, each a separate tenant with its own key, records and clients. Customers can verify messages from any enrolled bank in one place.

Operations

  • Start-up checks. All configuration is validated before the service starts and every problem is reported at once. The store is pinged before the service accepts traffic.
  • Health. GET /health answers 200 while the store is reachable and 503 when it is not.
  • Metrics. GET /v1/metrics returns registrations by category, verifications by verdict and channel, link and call checks, open calls and report counts.
  • Fraud desk email. New and growing campaigns, approved advisories, an on-demand activity summary and a welcome message go to the bank's alert addresses through Resend.
  • Live checks. A server check command tests the store, token keys, AI provider, push and email with the live credentials.
  • Expiry. Firestore time-to-live policies delete expired records; reads also enforce expiry, so an expired record never matches even before deletion.
